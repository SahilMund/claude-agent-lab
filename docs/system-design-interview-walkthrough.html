How I'd explain claude_agent_lab in 35 minutes

A script for narrating this project's system design end to end — requirements first, then architecture, then the decisions an interviewer will actually probe: RAG vs. grep, short-term vs. long-term memory, caching, MCP vs. plain tools, and why a task queue exists at all.

00

How to run this in the room

0:00–0:02

Before the design itself — the shape of a good answer to "walk me through a project you built."

  1. Say the one-liner first. "A local CLI that lets you ask natural-language questions about a codebase and get answers grounded in real code, plus an agent that can plan and execute multi-step engineering tasks against that same codebase." Everything else is detail on that sentence.
  2. State the two constraints that shape every later decision before describing components: this runs on one machine, for one user, at low cost. A lot of "why didn't you do X" questions dissolve once these are on the table.
  3. Draw the architecture diagram early (Section 2) — it's the map you keep pointing back to for the rest of the conversation.
  4. Volunteer the known gaps yourself (Section 14) rather than waiting to be caught. It reads as more senior than a spotless story.
01

Requirements

0:02–0:05

Functional requirements say what the system must do. Non-functional requirements say what shape the doing has to take — and in this project, the non-functionals are what actually decided the architecture.

Functional

  • Index a local, multi-language codebase into something searchable by meaning, not just text.
  • Answer natural-language questions grounded in real code, with file + line citations — never a bare hallucinated answer.
  • Hold a multi-turn conversation per session; resume a past one by ID.
  • Remember durable facts/preferences across sessions, not just within one.
  • Take a fuzzy multi-step goal, turn it into a plan, and execute it with a human approval gate.
  • Let the agent read/write files, run shell commands, and reach external services (GitHub) safely.
  • Keep the index fresh as the codebase changes — whether a human or the agent itself made the change.
  • Cache repeated or paraphrased questions to save cost and latency.
  • Swap the underlying LLM or embedding provider with a config edit, not a code change.
  • Package specialised "how-to" playbooks (skills) the agent loads only when relevant.

Non-functional

  • Local-first, single-user. No auth, no multi-tenancy — an explicit scope cut, not an oversight.
  • Cost-bounded. Local embeddings by default; the task executor runs serially (one task at a time) on purpose — determinism and cost control over throughput.
  • Resilient to dependency failure. Redis down, an MCP subprocess hiccup, or a mid-task crash must degrade or recover — never take down the REPL.
  • Interactive latency for /ask. Bounded retrieval (top-k), reused MCP sessions, cache-first lookups.
  • Extensible by config or file drop, not by forking code — new LLM provider, new skill, new MCP server.
  • Auditable state. Every task transition is one atomic SQLite write, so a crash never leaves ambiguous state.
Say this

"Almost every interesting decision below is downstream of two things: it's single-user/local, and it has to stay cheap. Parallel task execution, a hosted vector DB, multi-tenant auth — all rejected or deferred because the non-functionals didn't call for them, not because they're hard."

02

A worked use case

0:04–0:07

Requirements are abstract until they're pinned to one concrete scenario. This is the scenario to actually narrate — it's what every later section is explaining the machinery for.

Clarifying questions worth asking out loud first

  • CLI for one developer, or something a team shares? → this project: single developer, single machine.
  • Typical repo size — hundreds of files, or a monorepo? → small-to-medium; the chunking/indexing choices in Section 6 assume this.
  • Risk tolerance for autonomous multi-file edits? → low enough to require human approval before any /plan executes.

The scenario

A developer opens a repository they didn't write. They want to (a) understand a subsystem before touching it, and (b) have the agent implement one small, well-scoped feature once they understand enough to trust it.

  1. Orientation, via /ask — "how does the config system work?" Hits Section 7's loop: cache check, search_codebase, a grounded answer with file/line citations. Zero risk — read-only.Sections 5, 7
  2. A follow-up in the same breath — "and how would I add a new field to it?" STM (Section 8) means this resolves the pronoun "it" correctly without re-stating context.Section 8
  3. A stated preference — "when you generate code, prefer early returns." The agent calls remember — not because this turn needs it, but because every future session should know it.Section 8, LTM
  4. Committing to the change, via /plan — "add a timeout_seconds field to the config, threaded through the retriever." Decomposed into a small DAG, presented for approval before anything is written.Section 12
  5. Execution, one task at a time — each task gets only the tools its type needs; the earlier remember'd style preference is available to every sub-agent via recall, not just the original session.Sections 8, 10, 12
  6. Verification, not trust — each task's output is judged against its own acceptance criteria before being marked done.Section 12
  7. Immediate re-grounding — the moment the plan finishes, a reindex runs so a follow-up /ask about the new field is answered from the real, current code, not stale context.Section 6
Common follow-up

"How do you stop this from making unbounded tool calls and running up cost?" — concretely, in this project: a 30-second timeout on every shell command, max_retries=3 per task, strictly serial task execution (one LLM agent running at a time, not N in parallel), and a judge gate that fails fast on a bad output rather than letting the orchestrator loop indefinitely re-trying a fundamentally wrong approach.

05

The core bet: RAG vs. grep

0:10–0:15

The single decision every other subsystem in this project hangs off: how does the agent find the code relevant to a question? There are two real answers, and most production coding agents you've used pick differently than this project does — worth addressing head-on.

Option ALexical / agentic search (grep-style)

  • No pre-processing at all — the agent is handed a grep/glob/read_file tool set and searches the live filesystem itself, iteratively, choosing its own search terms.
  • Always 100% fresh — there is no index to go stale, because there is no index.
  • As publicly described, this is the core approach Claude Code (Anthropic's own CLI) takes: it doesn't build a persistent embedding index of your repo by default — it leans on the model's own iterative tool-use (grep/glob/read) plus a large context window.

Option BRetrieval-augmented generation (what this project does)

  • Pre-process once: chunk the codebase into meaningful units (function/class/block), embed each chunk, store in a vector index.
  • At query time: embed the question, do one similarity search, hand the top-k chunks to the LLM as grounding — one retrieval step instead of many tool round-trips.
  • As publicly described, Cursor AST-chunks code and embeds it into a dedicated vector search engine, retrieved via semantic similarity. GitHub Copilot historically leaned on local context (current file + "neighboring tabs" similarity) for inline completions, with a pre-built semantic index added for chat/workspace-aware features.

Why RAG here
  • This is explicitly a systems-design learning project — the point is to build and understand the chunking → embedding → hybrid-retrieval pipeline itself. That subsystem doesn't exist to learn from under a grep-only design.
  • Tree-sitter chunking returns whole, AST-defined units (a full function or class, not an arbitrary line window) with clean metadata — nicer grounding for citations than an arbitrary grep match window.
  • Hybrid mode (dense + BM25 sparse) means it isn't purely semantic either — exact identifier lookups still work, closing RAG's classic "can't find getUserById if it's phrased differently" gap.
If I had to switch this project to grep-only — what actually changes
  • Delete context/indexers/, context/retrievers/, the Qdrant dependency, and the retrieval-embeddings config entirely.
  • search_codebase becomes a grep_codebase tool wrapping ripgrep as a subprocess — structurally identical to the existing run_command tool, which can already do this informally today.
  • No indexing step at startup → faster cold start, and the entire "index freshness" problem in Section 5 disappears — there's nothing to go stale.
  • Embeddings don't disappear entirely — the semantic cache and long-term memory both still want them, just not for code retrieval anymore.
  • Net cost shifts from "build/maintain an index" to "more LLM round-trips per question" — more tokens and latency per /ask, less infrastructure to run.
06

Indexing & keeping it fresh

0:15–0:19

Having chosen RAG, two problems follow immediately: how do you chunk code sensibly, and how do you stop the index from lying to you the moment a file changes?

Chunking

  • Code files (15 languages — Python, JS/TS/TSX, Java, Go, Rust, C/C++, C#, Ruby, PHP, Swift, Kotlin, Bash) are parsed with tree-sitter; the walk stops the moment it hits a function/class/method node, so nested functions aren't double-indexed as separate chunks.
  • Text/config files (.md, .yaml, .json, ...) have no meaningful AST — chunked with a 50-line sliding window, 10-line overlap, so context isn't lost at a boundary.
  • If AST parsing finds nothing in a code file (e.g. an imports-only file), it falls back to the same sliding window — every file produces at least one chunk.
  • Each chunk carries real metadata: file path, name, type, start/end line — what actually lets an answer cite factory.py:19-32 instead of a vague paraphrase.

Freshness — four separate triggers, not one

flowchart LR
    A["App startup"] -->|"collection already has points?"| A2{Skip full reindex}
    B["/reindex command"] --> IDXR["Full reindex"]
    C["File watcher\n(watchdog, 1.5s debounce)"] -->|"per-file upsert/delete"| G{"vector_store.provider\n== qdrant?"}
    G -->|"no (chroma)"| WORKS["Index updated ✓"]
    G -->|"yes — this project's default"| BROKEN["Gap: hardcoded to Chroma's\nper-file functions — no-op"]
    D["/plan finishes"] --> IDXR2["Explicit full reindex\n(provider-agnostic)"]

    style BROKEN fill:#a8402c14,stroke:#a8402c,stroke-width:1.5px
    style WORKS fill:#2c7a6716,stroke:#2c7a67,stroke-width:1.5px
  1. Startup — get_indexer()(repo_path) checks whether the collection already has points; if so it loads the existing index instead of re-embedding everything on every launch.
  2. Manual — the user runs /reindex for a full, provider-agnostic rebuild.
  3. The watcher, for human edits — a watchdog observer (FSEvents on macOS, inotify on Linux, polling on Windows) fires on file create/modify/delete/move.
  4. The explicit post-/plan reindex, for agent edits — after every task-execution run finishes, handle_plan_command calls the indexer again directly, regardless of which vector store is configured.

Why the watcher debounces, specifically

  • The problem: a single "save" in most editors doesn't fire one filesystem event — it fires several (a write, a permissions/chmod touch, sometimes a rename-swap for atomic saves). Reacting to each one naively means re-embedding the same file 2–3 times per keystroke-adjacent save, for no benefit.
  • The mechanism: every indexable file gets its own threading.Timer, armed for 1.5 seconds. If another event for that same file arrives before the timer fires, the old timer is cancelled and a fresh 1.5s timer starts — so the actual reindex call only fires once the file has been quiet for a full 1.5s.
  • Why per-file, not one global timer: editing two unrelated files back-to-back shouldn't make the second file's reindex wait on the first's debounce window — a shared timer would silently delay unrelated changes for no reason.
  • The actual payoff: without this, a burst of saves (or a large git checkout touching many tracked files at once) could fire a storm of overlapping, redundant embedding calls — wasted embedding-API cost and CPU, and a real risk of two overlapping reindex jobs racing on the same file.
Real, current gap

The watcher's on-change handler is hard-coded to Chroma's per-file update functions. With this project's actual default (vector_store.provider: qdrant, hybrid mode), a human editing a file does not reach the live index today — only /reindex or the post-/plan call does. Interesting asymmetry to volunteer: the agent's own edits stay fresh automatically; a human's edits currently don't, for the opposite of the reason you'd guess.

  • agent/factory.py assembles one LangChain create_agent graph: provider-agnostic LLM, the tool list (search_codebase, recall, remember, load_skill, terminal tools, ~40 MCP tools), a system prompt, and the LangGraph checkpointer for memory.
  • The system prompt is a direct policy, not a suggestion: "Always use the search_codebase tool before answering any question" — grounding is enforced by instruction, not left to the model's discretion.
  • The cache check happens before the agent is touched at all — a hit means zero tool calls, zero LLM calls, zero retrieval.

The LLM call itself — input and output shape, and why

"Reasoning turn" in the diagram above is one HTTP call to the provider's chat-completions endpoint. Same input/output shape on every one of those calls, whichever provider llm/factory.py picked.

WhatWhy this shape
Input
  • System message — SYSTEM_PROMPT + skills prompt, one string, sent once per call (not re-derived each turn).
  • Message history — the ordered list from the checkpointer's messages channel: HumanMessage (user turns), AIMessage (past reasoning + tool calls), ToolMessage (past tool results) — summarized/trimmed per Section 8's STM card once it crosses 4,000 tokens.
  • Tool schemas — every @tool-decorated function's name, docstring, and typed args, converted to JSON Schema and bound to the model (create_agent calls the provider's own bind_tools). This is how the model "knows" search_codebase(query: str) exists at all.
Nothing here is a special "memory" input — STM enters as ordinary messages already in the list; LTM enters only if recall was called on a previous turn, as a ToolMessage like any other tool result. One list, one shape, easier to reason about than a system with several distinct injection channels.
Output One AIMessage per call, one of two shapes:
  • Tool-call turn: .tool_calls populated — a list of {name, args, id}, where args is JSON already parsed and validated against that tool's schema.
  • Final turn: .tool_calls empty, .content is the plain-text answer — the graph's exit condition for the loop.
Structured tool_calls (native function-calling on the provider side) beats asking the model to emit an ad-hoc string like "ACTION: search_codebase(query=...)" and regex-parsing it — the provider guarantees the JSON matches the declared schema instead of this app having to defensively parse free text. It's also what makes the five-provider swap in Section 4 a config-only change: LangChain normalizes each provider's own function-calling wire format to this same AIMessage.tool_calls shape, so nothing downstream of get_llm() needs to know which provider actually answered.
Name it

That reasoning ↔ tool-call loop is the textbook ReAct pattern (Reason, Act, Observe, repeat) — and the /ask vs. /plan split one level up in main.py is Routing, just a deterministic command-prefix router rather than a learned/LLM classifier. Both get their full lineup of names in Section 13.

08

Short-term vs. long-term memory

0:22–0:25

Two genuinely different problems that are easy to conflate: "remember this conversation" and "remember this fact forever."

Short-term (STM)

  • What: the full message history of one conversation, keyed by thread_id.
  • Where: LangGraph's AsyncSqliteSaver → .agent_lab/memory/memory.db. Which thread is "current" is a separate one-line text file, .agent_lab/memory/current_session.
  • Bounded automatically: past 4,000 tokens, SummarizationMiddleware compresses older turns and keeps the last 20 messages verbatim — a long session never blows the context window.
  • Scope: per-thread only. /new_session starts a fresh, empty thread; /switch <id> resumes an old one — nothing is deleted, just not currently active.
  • Used for: "what did I just ask", multi-turn follow-ups — never crosses a session boundary on its own.

Long-term (LTM)

  • What: durable facts/preferences, written and read explicitly via two agent tools — remember(fact, category) / recall(query, k).
  • Where: a separate Qdrant collection (claude_agent_lab_memory) from the code index — same embedder, different collection.
  • Scope: global — not tied to thread_id at all. A fact saved in session 1 is retrievable in session 47.
  • Retrieval is explicit, not automatic: the model decides to call recall; nothing is silently injected into every prompt.
  • Known gap: no de-duplication, no expiry/forgetting — unlike the semantic cache's TTL, a contradicted fact just sits alongside the new one.

Why not auto-inject LTM every turn?

Considered and rejected: always running recall(question) before every turn guarantees nothing relevant is missed, but costs an embedding + vector search on every single question, even ones with no relevant history, and makes "why did the model bring this up" invisible — not a traceable tool call, just silently-added context. Explicit tool calls cost nothing when irrelevant and stay visible in the same trace every other tool call already produces.

09

Caching

0:25–0:27

Not a string-match cache — a semantic one, because two people rarely ask a question the same way twice.

Why bother, specifically

  • Every /ask miss costs an embedding call, a Qdrant search, and a full LLM generation — the three most expensive, slowest steps in the whole system, paid in full on every single question.
  • Real usage clusters: the same handful of questions ("how does X work," "where is Y configured") get asked repeatedly, worded slightly differently each time — a plain exact-match cache would miss almost all of that repetition; a semantic one catches it.

How it's actually built here

  • Backed by Redis + RediSearch (via redisvl): each cached entry stores a query embedding (HNSW index, cosine distance) alongside the response.
  • A lookup embeds the incoming question, finds the nearest cached query, and only returns it if similarity ≥ threshold (default 0.85) — a near-miss is treated as a cache miss, not a wrong answer.
  • Filtered on two tags at once: domain (a hash of the repo path, so two different projects indexed by the same install never collide) and model (a cached answer from Claude is never served under Groq — correct behaviour when the provider is a config-only switch, per Section 4's cousin decision).
  • Each entry has a TTL (default 24h); Redis expiry handles cleanup — no manual garbage collection.
  • Invalidated by domain when the codebase changes — wired to the same watcher callback as Section 5, so it currently inherits that section's Qdrant-vs-Chroma gap too.
  • Degrades gracefully, on purpose: if Redis is unreachable, or reachable but missing the RediSearch module (plain redis-server doesn't ship it — Redis Stack does), build_semantic_cache() catches the failure and returns None. The whole app runs fine with caching simply off, rather than crashing at startup.

Tools vs. MCP — and whether MCP earns its place

0:27–0:29

Two ways to give the agent a capability, with genuinely different cost profiles — and this project's own MCP setup has a real redundancy worth naming out loud.

In-process toolMCP server
Examples hereread_file, write_file, run_commandgithub, filesystem (both via npx / stdio)
RunsSame Python process, plain function callSeparate subprocess, JSON-RPC over stdio
Cost per callNear zeroA live session round-trip; naive reconnect-per-call can even respawn the subprocess (a real bug hit and fixed in this project — see callout)
Best forLocal, fast, fully-trusted capability you're happy to own and secure yourselfA capability that lives behind someone else's maintained protocol server — not worth reimplementing or re-securing
  • The GitHub MCP server earns its place: nothing in-process replicates "open a PR," "search code across GitHub," "list issues" — that's exactly the case MCP is for.
  • The filesystem MCP server substantially overlaps tools/filesystem_tools.py, which already does read/write/list in-process. Genuinely redundant today — a fair "what would you cut" answer.
  • Both servers are launched via npx; the filesystem one is sandboxed to the current working directory by its own startup args (the client doesn't implement MCP's dynamic "Roots" negotiation, so it falls back to that static scope — which is exactly the scope wanted here).
Lesson learned the hard way

The MCP client library's simplest API opens a new session per tool call by design — for a stdio server that means respawning the whole subprocess on every single call. Fixed by holding one session per server open for the app's entire lifetime instead. General lesson: MCP tools have a process/network cost that in-process tools don't, and a "stateless-looking" client API can hide a very stateful, very slow default.

Skills — progressive disclosure

0:29–0:31

A lazy-loading pattern applied to prompt context: pay for detailed instructions only on the turns that actually need them.

Why this matters at all

  • The system prompt already carries a real, fixed cost every single call: the base instructions, the memory policy (Section 8), and now the tool definitions for ~46 tools (Section 10). Every additional capability described in full, permanently, in that same prompt makes every call — even a trivial one — more expensive and slower, whether or not that capability is used this turn.
  • Skills exist to break that link: a specialised, verbose playbook (a debugging procedure, a project-specific test-writing convention) should cost tokens only on the turns that actually need it — not on the other 99% of calls that don't.

Tier 1 — always paid

  • System prompt carries only name + description + when_to_use per skill — a few tokens each, every single call.

Tier 2 — on demand

  • Model calls load_skill(name); the full SKILL.md body (500–2,000 tokens) enters context only for that turn.

Tier 3 — on demand

  • If the skill references support files (scripts/templates), the model reads them individually with the existing read_file tool.
  • Without skills: every specialised instruction the agent might ever need has to live permanently in the system prompt — cost scales with everything the agent could be asked, not what it's doing right now.
  • With skills: the system prompt carries a one-line index; a whole debugging playbook or test-writing template is loaded exactly when it's relevant.
  • Tradeoff: quality depends on the description/when_to_use metadata being good enough for the model to self-select correctly — a vague description means a skill that silently never fires.
How this project actually uses it, today

Honestly: the infrastructure is fully built and wired into the agent (SkillRegistry, the load_skill tool, the three-tier loading path above) — but no SKILL.md ships with the project yet, and .agent_lab/skills/ doesn't exist until someone creates it. build_skills_prompt() correctly returns an empty string and logs "skills_dir not found... No skills loaded" rather than erroring. This is a real, current gap worth naming plainly rather than implying skills are in active use: the mechanism is proven and tested, the content library is empty.

Long-running tasks — why /plan exists at all

0:31–0:34

A single agent turn is the wrong unit of work for "scaffold this feature" — too big to verify at once, too risky to run unsupervised, and it needs to survive being interrupted.

  • Decompose a fuzzy goal into a verifiable DAG — the planner's own system prompt enforces ordering (architecture → schema → config → core → tests → integration) and concrete acceptance_criteria per task.
  • Human approval before any code is written — [A]pprove / [M]odify / [R]eject loop; a rejection re-plans with the human's stated feedback.
  • Least-privilege tools per task type — a design task can't run shell commands; a test or integrate task can.
  • Don't trust the sub-agent's own "I'm done" — an LLM-as-judge (cheaper judge_model) scores the output 0–10 against that task's own acceptance criteria; below 6, it's rejected and retried automatically.
  • Survive a crash without ambiguity — state lives in SQLite (WAL mode), not memory; every transition is one atomic UPDATE.
  • Resume exactly where it left off — on restart, any task still in_progress is unconditionally orphaned (single-process serial execution means the process that owned it is simply gone) and reset to pending (retries left) or failed (exhausted) — no heartbeat mechanism needed.
  • Reindex when it's done — so /ask can immediately answer questions about files the plan just created (this is the "explicit reindex" trigger from Section 5).
stateDiagram-v2
    [*] --> pending
    pending --> in_progress: claim_task()
    in_progress --> completed: judge passed
    in_progress --> pending: judge failed, retries left
    in_progress --> failed: retries exhausted
    pending --> blocked: a dependency failed
    completed --> [*]
    failed --> [*]
    blocked --> [*]
    skipped --> [*]
Why serial, not parallel

max_concurrent=1 is a deliberate choice, not a limitation. Most tasks are sequentially dependent anyway (schema before core, core before tests), shared repo state makes true parallel writes risky, and N parallel LLM agents multiplies cost for work that mostly has to happen in order. Revisit only once cost stops being the binding constraint.

Naming the architecture — the vocabulary interviewers reach for

0:33–0:35

Everything in Sections 7–12 already implements a small set of well-known agentic workflow patterns (per Anthropic's own "Building Effective Agents" taxonomy, plus the standard HITL/ReAct vocabulary). Naming them precisely — including the ones deliberately not used — is exactly what separates "I built an agent" from "I can reason about agent architecture."

PatternUsed here?Where
ReAct (Reason → Act → Observe, repeat)✓ core loopEvery agent turn — both the /ask agent (Section 7) and each /plan sub-agent (Section 12) run the identical LangGraph ReAct loop
Tool Use✓ foundationalEverything is a tool call — retrieval, memory, filesystem, shell, MCP — nothing is a silent side effect (Section 10)
Routing✓ but deterministic, not learnedmain.py's command dispatch (/ask vs. /plan vs. /reindex) — a plain string-prefix switch, not an LLM/classifier deciding the route

The honest caveat

Calling the judge/retry loop a full Evaluator-Optimizer pattern slightly overstates it. In Anthropic's own definition, the optimizer step uses the evaluator's feedback to refine the next attempt. Here, fail_task() records the judge's rejection reason in the error column — but _build_system_prompt() never actually reads that field back into the retried task's prompt. The retry is a fresh, blind attempt at the same instructions, not a refinement informed by why it failed last time. A one-line fix (thread task['error'] into the retried prompt as "your previous attempt was rejected because...") would close this gap and make it a true Evaluator-Optimizer loop — exactly the kind of precise, self-aware distinction worth volunteering rather than letting an interviewer catch.

If asked "why no fan-out?"

The honest answer, not a dodge: independent subtasks (e.g. writing two unrelated config files) could fan out and join back once both complete — nothing about the DAG model in Section 12 prevents it. It doesn't today because max_concurrent=1 was chosen deliberately for cost and determinism (Section 12), not because the orchestrator is incapable of it. Section 17 names exactly what adding it back would look like.

LLD & the practices actually followed

0:33–0:36

Zooming from architecture into the actual classes, schemas, and error-handling conventions — the level a good LLD round probes.

Core data models

Structured LLM output (Pydantic)

  • PlannedTask — id, title, description, task_type, depends_on, output_files, acceptance_criteria, estimated_minutes
  • ExecutionPlan — project_name, goal_summary, tech_stack, tasks: list[PlannedTask], risks, assumptions
  • _JudgeVerdict — passed: bool, score: 0–10, reason: str

Persistence schema (SQLite)

  • projects(id, name, goal, plan_json, status, approved_at)
  • tasks(id, project_id, status, depends_on, output_files, acceptance_criteria, retry_count, max_retries, execution_order, result, error)
  • Index on (project_id, status) — the exact pair every scheduling query filters on

Two different error-handling conventions, on purpose

ConsumerConventionWhy
An LLM, via a tool callReturn a plain "Error: ..." string, never raiseA raised exception would crash the agent graph; a returned string becomes a normal tool result the model can read and self-correct from
Internal control flow (the task executor)Raise ValueError on judge rejection or empty outputThis is meant to be caught — it's exactly the signal TaskOrchestrator._execute's existing try/except uses to trigger the retry path in fail_task()

Best practices this project actually follows

  • Factory functions for every swappable backend — get_llm(), get_embedder(), get_indexer(), get_retriever() each hide an if/elif behind one call, so callers never know or care which provider is live.
  • Dataclasses/Pydantic at every structural boundary — ParsedChunk, Task, PlannedTask/ExecutionPlan — so a chunk or a task is a typed shape passed around, never a loose dict with implicit fields.
  • Context-manager-scoped DB connections — SQLiteTaskStore._conn() opens, commits/rolls back, and closes a connection per operation; no shared long-lived connection to leak across threads.
  • Atomic single-UPDATE state transitions — claim_task()'s WHERE status='pending' clause makes the claim itself the concurrency guard, no separate lock needed.
  • Least-privilege by construction — _TOOLS_BY_TYPE is a dict literal, not a runtime permission check; a design task's agent is never even handed a shell-executing tool to misuse.
  • Graceful degradation returns None, doesn't crash — build_semantic_cache() catches Redis/module failures; a value of None is a first-class, checked case at every call site, not an exceptional one.
  • One config dict, read once — every module imports the same already-parsed config object rather than re-reading config.yaml, so a run is internally consistent even if the file changes on disk mid-session.

Future work: scaling, cost & evals

0:38

None of this is needed at today's actual scale (single user, single machine) — but naming what changes, and why, is exactly what an interviewer is checking for.

CostCost optimization

  • Prompt/KV caching — a real, unclaimed opportunity here. The system prompt + tool definitions + the skills index (Section 11) are largely static across an entire session. Marking that block cacheable (Anthropic requires explicit cache_control breakpoints; OpenAI detects repeated prefixes implicitly) turns every call after the first into a cache-hit-priced call for that block — roughly a 0.1× multiplier on that portion versus full price, against a 1.25× multiplier paid once on the first call to write it. Not yet done in this project.
  • The judge-model pattern, generalized. llm.judge_model already uses a cheaper model for a narrower job (score a task against acceptance criteria) — the same pattern could grade /ask answers for faithfulness without paying full-model price for every check.
  • Watch the parallelism gotcha. Firing several cacheable calls at once, before the first has finished writing the cache, means none of them get the hit price — they all race past an empty cache. A single sequential warm-up call first avoids this.

LatencyCaching at every layer, not just one

This project caches exactly one layer today — the final LLM response (Section 9). A fuller pipeline caches independently at each stage, since each is deterministic-ish for a given input:

flowchart LR
    Q["Query"] --> EC{"Embedding\ncache?"}
    EC -->|hit| RC
    EC -->|miss| EMB["Embed query"] --> RC{"Retrieval\ncache?"}
    RC -->|hit| GEN
    RC -->|miss| VDB["Search vector store"] --> RR{"Rerank\ncache?"}
    RR --> GEN{"Semantic\nresponse cache?\n(this project has this one)"}
    GEN -->|hit| DONE["Return cached answer"]
    GEN -->|miss| LLM["LLM generates"] --> DONE
    style GEN fill:#2c7a6716,stroke:#2c7a67,stroke-width:1.5px
  • Embedding cache — the same question text always embeds to the same vector; skip re-embedding an exact repeat.
  • Retrieval cache — the same embedding, against an unchanged index, returns the same top-k; worth caching between reindex events.
  • Reranking — a real gap: this project's hybrid mode fuses dense+sparse scores but has no dedicated cross-encoder reranking pass at all today. Worth adding before worth caching.
  • Response cache — already built (Section 9).

ThroughputTurning on Parallelization (fan-out/fan-in) for /plan

flowchart LR
    T["Ready tasks:\ntask_003, task_004, task_005\n(no unmet dependencies)"] --> F{"Fan out"}
    F --> W1["Worker agent\ntask_003"]
    F --> W2["Worker agent\ntask_004"]
    F --> W3["Worker agent\ntask_005"]
    W1 --> J["Fan in — join point:\nwait for all three, then\nunblock whatever depended on them"]
    W2 --> J
    W3 --> J
  • The DAG model in Section 12 already tracks exactly which tasks are mutually independent (get_ready_tasks() returns all of them, not just one) — TaskOrchestrator._execute would just need to dispatch that whole ready batch via asyncio.gather instead of slicing to [:max_concurrent] with max_concurrent=1.
  • The real cost of turning this on isn't code — it's the two things Section 12 already named as the reason it's off: N parallel LLM calls billed simultaneously instead of one at a time, and shared-repo write safety once two worker agents can touch the filesystem concurrently.

Scale-outSharding — not needed today, but here's the reasoning

flowchart TD
    Qy["Query"] --> S1["Shard: auth/"]
    Qy --> S2["Shard: payments/"]
    Qy --> S3["Shard: ui/"]
    S1 --> M["Merge & re-rank"]
    S2 --> M
    S3 --> M
    M --> R["Final top-K"]
  • A single Qdrant instance comfortably holds this project's own 185-chunk index — sharding would be pure overhead here.
  • Past the point one instance can't hold or serve the volume: semantic sharding (partition by module/domain, e.g. one shard per top-level package) beats random hash-based sharding, because a query whose domain is known can route to just the relevant shard instead of a full scatter-gather.
  • Scatter-gather's real cost: querying every shard and merging centrally means end-to-end latency is bounded by the slowest shard, and a disproportionately-hot shard (the module everyone asks about) needs its own replication, not just a bigger box.

QualityEvals & LLM-as-judge, expanded

  • Today's judge is narrow by design — it only scores /plan task output against that task's own acceptance criteria. There is no regression eval at all for /ask's retrieval or answer quality.
  • What a fuller eval loop would add: a small hand-built golden set for this repo — (question, correct source chunk) pairs — scored on Precision@K/Recall@K/MRR for retrieval, plus faithfulness (does the answer only claim what the retrieved chunks actually support?) as a separate axis from factuality (is it true in reality?) — a stale-but-consistent retrieved chunk can produce a faithful yet wrong answer, and that's a retrieval/freshness bug (Section 6), not a generation bug.
  • Wire it in as a CI gate, in the same "verify before shipping" spirit this project already practiced live — every fix in this document (the Qdrant HTTPS bug, the Groq model_name field, the MCP session-reuse bug) was confirmed against a real running instance before being called done, not assumed correct from reading the code. An offline eval threshold before any prompt/retrieval/model change ships is the same discipline, automated.
  • Then the rollout ladder, only after the offline gate passes: shadow (new version sees real traffic, output never shown — zero user risk) → canary (5%→25%→50%→100% of real traffic, watching for regressions) → full rollout. Skipping straight to canary skips the one step that's genuinely free.

Deployment

0:39

What actually shipped this session, and the concrete next step to make it deployable beyond one developer's laptop.

Today, as actually run

  • One machine, one user: the package installed locally (poetry install / pip install -e .), three local services — Qdrant, Redis Stack, optionally Ollama — each started by hand.
  • No auth boundary, no process supervision, no restart policy — entirely appropriate for the stated non-functional requirements (Section 1), and worth saying so plainly rather than apologizing for it.

Next concrete step — still single-machine, but reproducible

Bundle the two real dependencies into one docker-compose.yml instead of manual docker run commands, following the same lessons this session hit in practice (pin versions, never latest; bind-mount volumes so data survives a restart; set restart: unless-stopped):

services: qdrant: image: qdrant/qdrant:v1.12.0 restart: unless-stopped ports: ["6333:6333"] volumes: ["./data/qdrant:/qdrant/storage"] redis: image: redis/redis-stack-server:7.4.0-v3 restart: unless-stopped ports: ["6379:6379"] volumes: ["./data/redis:/data"]

If this ever became a hosted, multi-user product

A hosted HTTP front end (a FastAPI dashboard was built as Phase 8, then removed for reliability reasons) would be the front door for this — but three assumptions from the single-user design would need to change first, on top of rebuilding that front end properly:

  • SQLite → Postgres for task/session state. WAL mode is genuinely fine for one writer + concurrent readers on one machine; it doesn't help once multiple app instances need to see the same task queue across a network.
  • Separate the API process from /plan execution. A long-running task shouldn't block a request/response HTTP cycle — move task execution to a background worker process, with the API only enqueuing and polling status.
  • Tenant isolation on the vector store. Either a dedicated Qdrant collection per customer (strongest isolation, doesn't scale past a handful of tenants) or one shared collection with a mandatory, server-derived tenant_id metadata filter baked into the query path itself — never trusted from client input, enforced at both the application layer and the DB-query layer so one missed filter clause can't become a cross-tenant data leak.
  • Every prompt/model/retrieval change ships through the rollout ladder from Section 16 — offline eval gate, then shadow, then canary — rather than straight to 100% of a live customer base.

Glossary

RAG
Retrieval-Augmented Generation — fetch relevant context via search, then generate an answer grounded in it.
MCP
Model Context Protocol — a standard for LLM apps to talk to external tool servers over a common (often stdio/JSON-RPC) interface.
STM / LTM
Short-term memory (this conversation) vs. long-term memory (facts that outlive any one conversation).
Hybrid retrieval
Combining dense (embedding/cosine) search with sparse (BM25/keyword) search so both meaning and exact terms are found.
HNSW
Hierarchical Navigable Small World — the approximate-nearest-neighbour index structure behind fast vector search.
Checkpointer
LangGraph's mechanism for persisting an agent's conversation state between calls, keyed by thread ID.
DAG
Directed Acyclic Graph — here, tasks with dependencies but no circular waits.
Debounce
Wait until events stop arriving before acting — avoids reacting to every intermediate filesystem event from a single save.
WAL mode
SQLite's Write-Ahead Log — crash-safe, allows concurrent reads while a write is in progress.
LLM-as-judge
Using a (often cheaper) LLM call to score another LLM's output against explicit criteria, instead of trusting a self-report.
ReAct
Reason → Act → Observe, repeat — the core loop behind almost every tool-calling agent, this one included.
HITL
Human-In-The-Loop — an explicit pause point where a person must approve before the system proceeds.
Orchestrator–Workers
A central process dynamically decomposes a goal and dispatches fresh worker agents per subtask — for goals whose subtasks can't be predicted upfront.
Evaluator–Optimizer
One LLM call generates, a second evaluates against criteria and feeds back into a refinement loop — not just a pass/fail gate with a blind retry.
Fan-out / fan-in
Dispatch independent work concurrently ("fan out"), then wait for all of it before continuing ("fan in") — the mechanics behind the Parallelization pattern and behind scatter-gather across shards.
